# Шабашка

Доска объявлений для поиска подработки и мастеров в Кыргызстане.

- **Заказчики** регистрируются (по email) и размещают заказы.
- **Исполнители** ничего не регистрируют — они просто смотрят заказы и пишут заказчику
  напрямую в WhatsApp кнопкой на странице заказа.
- Есть **вакансии** (постоянная/частичная работа) — параллельно с разовыми заказами.
- Есть **админ-панель** для модерации (пользователи, заказы, вакансии, жалобы, категории).

Архитектура сделана как REST API + отдельный веб-фронтенд, чтобы тот же бэкенд
можно было потом переиспользовать для мобильного приложения на React Native.

## Стек

- **backend/** — Node.js, Express, PostgreSQL (`pg`, для Neon/Supabase), JWT-авторизация
- **frontend/** — React (Vite), React Router

## Возможности

- Регистрация/вход заказчиков по email, отдельный номер WhatsApp для связи
- Публикация заказов и вакансий: категория, город, примерный адрес, бюджет/зарплата
- Лента заказов/вакансий: поиск, фильтры, сортировка, пагинация
- Просмотры, закреплённые ("🔥 Топ") объявления
- Избранное — работает без регистрации, хранится в `localStorage` браузера
- Редактирование/закрытие/удаление своих объявлений
- Жалобы на заказы, вакансии и записки с доски ("Пожаловаться") — без регистрации
- Админ-панель: статистика, пользователи (блокировка), заказы/вакансии (скрыть/закрепить),
  жалобы (модерация), категории (добавление/удаление)

## Что защищает площадку от ответственности за чужой обман

Сайт — посредник: объявления пишут пользователи, сделки идут вне сервиса. Посредник
не отвечает за чужой контент, пока он не знал о нарушении, убрал его после того как
узнал, и не выдавал чужое объявление за проверенное им самим. Всё, что для этого нужно
в коде, собрано в четырёх местах.

**Кнопка «Пожаловаться» на всём.** Была только у заказов — теперь есть у вакансий и у
записок на доске (`POST /api/{orders,vacancies,board}/:id/report`, все три без
авторизации: обманывают обычно исполнителя, а он на сайте не регистрируется). Жалоба
одновременно уходит в Telegram админам — см. `telegram/notify.js`. Ждать, пока кто-то
зайдёт в админку, нельзя: вся защита в том, что нарушение убрали быстро.

**Жалоба переживает объявление.** Раньше `reports` ссылалась на `orders(id) ON DELETE
CASCADE`, и после удаления заказа от разбора не оставалось ничего. Теперь ссылка
полиморфная (`listing_type`/`listing_id`, как в `conversations`), без внешнего ключа, и
вместе с жалобой сохраняется `snapshot` — копия объявления на момент подачи. Пока
жалобу разбирают, автор успевает поправить текст, а записка на доске вообще живёт
сутки.

**Журнал модерации** (`moderation_log`, см. `moderation.js`). Всё, что снимают с сайта —
из админки или кнопкой в боте, — уходит туда вместе с полной копией строки. Это
единственный способ ответить на вопрос «что там было написано и как быстро вы это
убрали» после удаления. Заказ и вакансию по жалобе не удаляем, а закрываем, записку на
доске — скрываем (`hidden`): объявление с жалобой само себе доказательство.

**Пометка импортированных объявлений** (`is_imported` у orders, vacancies, board_posts).
Бот публикует чужие объявления от имени администратора, и без пометки это выглядит как
объявление, поданное на сайт и кем-то проверенное — ровно та подмена, из-за которой
площадка перестаёт быть посредником. На карточке стоит «Объявление взято из открытых
чатов. Автора мы не проверяли», на доске — «ℹ️ Из открытых чатов». Рядом с телефоном
в любом объявлении — предупреждение про предоплату (`SafetyNote.jsx`): почти все истории
«меня обманули» начинаются с перевода вперёд.

Всё это описано и в «Условиях использования» (`frontend/src/pages/Terms.jsx`): роль
сервиса, отсутствие проверки авторов, объявления из открытых источников и порядок
удаления по просьбе автора, порядок работы с жалобами.

> Это не юридическая консультация. Как перечисленное выглядит по законам КР и нужна ли
> регистрация ИП/ОсОО для площадки с объявлениями — вопрос к юристу, а не к README.

## Локальный запуск

```bash
npm run install:all
```

Нужна база Postgres (можно бесплатный проект на [Neon](https://neon.tech) или
[Supabase](https://supabase.com) — см. раздел про деплой ниже). Скопируйте
`backend/.env.example` в `backend/.env`, впишите `DATABASE_URL` и свой `JWT_SECRET`.

В двух терминалах:

```bash
npm run dev:backend
```

```bash
npm run dev:frontend
```

Backend поднимется на `http://localhost:4000`, фронтенд — на `http://localhost:5173`
(Vite проксирует `/api` на бэкенд, см. `frontend/vite.config.js`). Таблицы создаются
автоматически при первом запуске бэкенда.

### Тесты

```bash
npm test
```

Запускает `node --test` в `backend/test` — встроенный в Node тестовый раннер,
без зависимостей. Тесты покрывают то, что ломается молча и замечается только в
чате: суточную норму публикаций, запас токенов под рекламу, фильтр заграницы,
очередь разбора с её сторожем зависших задач, очередь роликов, разбор ответа
модели, переход на запасную модель, нарезку длинных сообщений Telegram и
подписи к постам.

**К базе тесты не ходят и ходить не должны.** `DATABASE_URL` в `backend/.env`
указывает на боевой Postgres, и тест, который случайно до него дотянется,
напишет или удалит что-нибудь в живых объявлениях. Поэтому любой `require`
внутри `src/db` из теста падает с внятной ошибкой (см. `test/helpers/stub.js`),
а модулям, которым база всё-таки нужна, подсовывается заглушка. По той же
причине бэкенд не запускают локально просто «посмотреть».

### Демо-данные

```bash
cd backend
npm run seed
```

Полностью очищает таблицы users/orders/vacancies/reports и заполняет их реалистичными
данными: ~13 пользователей, ~40 заказов и ~15 вакансий по всем категориям и городам,
несколько жалоб. Пароль всех демо-заказчиков — `password123`. Админ создаётся тем же
скриптом: `admin@shabashka.kg` / `admin12345`.

Чтобы создать/повысить администратора вручную:

```bash

```

## Импорт объявлений через Telegram-бота

Бот принимает пересланные сообщения из чатов и текст объявления,
разбирает их через Groq в поля заказа и **публикует сразу** — на сайт, в
Telegram-канал, текстом в Threads и, последним, роликом в Instagram. Подтверждения
нет: текст на входе, опубликованное объявление на выходе.

Ничего не переспрашивается и когда данных не хватает: город без ответа становится
«Бишкек», незнакомая категория — «Другое», отсутствующий заголовок собирается
из первой фразы описания. Что именно дописали, бот пишет в ответе — подмена
не должна проходить молча.

Куда попадёт объявление, решает `listing_type` из разбора. Заказ и вакансия
становятся карточками на сайте. Всё остальное, что всё-таки является объявлением —
продажа дома или машины, аренда, «делаем ремонт под ключ», поиск работы для себя,
грузоперевозки, — уходит на **доску**: у такого на сайте карточки нет, а выбрасывать
его жалко, потому что публика у него та же. На плашке ролика такое объявление
подписано «ДОСКА №24» синим — не «объявление»: так сразу видно, куда идти на сайте,
и сколько объявление там проживёт.
Ролик, пост в Telegram-канале и ссылка
для WhatsApp делаются точно так же, разница только в адресе: у записки на доске
своей страницы нет, поэтому ссылка ведёт на `/board#p123`, а страница подсвечивает
нужное объявление. Живёт записка сутки — ролик её переживёт, и по ссылке из
старого поста доска честно скажет, что объявление пропало.

В подписи к ролику и в посте в Threads обязательны две вещи: **номер**, если он
есть в объявлении, и **ссылка** на карточку или доску. Без номера откликнуться из
ленты Instagram нечем — ссылки там не кликабельные, — а без ссылки не найти само
объявление. На кадр ролика телефон по-прежнему не выносится (см. ниже).

Одно и то же объявление автор рассылает сразу в несколько чатов, и приходит оно
пачкой — повторы бот режет по телефону и сжатому заголовку
(`dedupHash` в `backend/src/telegram/imports.js`). Окно у этой проверки — **час**,
а не «навсегда», как было сначала. Смысл у неё остался ровно один: не дать одному
объявлению из пачки встать на сайт тремя карточками, тремя постами в
канале и тремя роликами (последнее ещё и втрое жжёт часовой лимит Meta). Всё, что
старше часа, публикуется заново без вопросов: объявления живут долго, их постят
повторно, и мешать этому нечем. Записки на **доску** от проверки освобождены
совсем — там продают и сдают одно и то же изо дня в день.

Плата за автопубликацию — отсутствие модерации до неё: в чатах хватает сообщений,
которые объявлениями не являются, а чужой телефон попадает на сайт без ведома
владельца. Единственным фильтром остаётся сама модель, поэтому промпт требует
от неё осторожности: должно быть понятно, что именно предлагают или ищут. Отдельным
правилом отсеивается запрещённое — наркотики, «лёгкие деньги» без объяснения работы,
ставки, займы под проценты, обмен валют, продажа документов, — и оно же не даёт
такому проскочить на доску под видом объявления. Нечитаемый или обрезанный до
бессмыслицы текст тоже отбраковывается, чтобы модель не восстанавливала содержание
по догадке.

Отдельно — **вербовка под видом уборки**. В сентябре 2026 бот выложил два таких
объявления, и в комментариях под постом в Threads их опознали раньше, чем мы: «это
сутенёры». По форме это безобидная подработка, поэтому в промпте описан признак,
которого у настоящей уборки не бывает: **не назван объект**. Настоящее объявление
говорит, что и где убирать (квартира после ремонта, кафе, офис, подъезд), а
вербовка — только «уборка», зато с деталями другого рода: ищут именно девушек
(«кыздар», «келиндер»), деньги «сразу наличными», вместо адреса ориентир или базар,
зовут писать в личку, названы возраст и внешность, платят заметно больше обычного.
Нет объекта плюс хоть один такой признак — объявление не публикуется. Правило
специально перекошено в сторону отказа: уборщица пришлёт объявление заново, а
опубликованная вербовка — это живые люди, которых к ней привели мы. Рекламная
приписка `/ad` этот запрет не снимает, в отличие от остального отсева.

Отдельно — **работа за границей**. Её не публикуем нигде: ни из чатов, ни по `/ad`,
ни с формы на сайте. Отправлять людей на работу за рубеж в Кыргызстане вправе
только агентства с разрешением Минтруда, закон «О внешней трудовой миграции»
(ст. 29) за рекламу такого набора спрашивает и со СМИ, а «работа в Корее, билет
оплатим» — обычный ход вербовщиков. Проверить агентство мы не можем.

Правило стоит в двух местах. В промпте — чтобы модель понимала смысл, а не
отдельные слова. И в `backend/src/abroad.js` — проверкой по словам, которая не
зависит ни от модели, ни от её лимитов: срочная реклама, ролики и картинки идут
мимо разбора вовсе. Проверка ищет страны и города, куда чаще всего едут на
заработки, в русской и кыргызской форме («в Москве», «Кореяга», «чет өлкөдө»,
«за рубежом»). Заказу и вакансии хватает одного названия, записке на доске и
рекламе нужны ещё слова про работу — иначе под запрет попали бы «одежда из
Турции» и «туры в Дубай». По той же причине до поиска вырезается то, что местом
работы не является: откуда товар («из Турции и Китая»), название заведения
(кафе «Сеул») и валюта («долларов США»). Слово, на котором сработала проверка,
бот пишет в отказе — ошибку видно сразу.

После отказа модели по рекламе бот обычно выкладывает её «как есть»: это
запасной ход на случай, когда разбор не справился. Для заграницы он отключён —
отказ помечается (`abroad` в разборе), и вместо публикации бот пишет причину.
Что нарисовано на самом макете, бот не читает: картинку с «работой в Корее» без
подписи он не поймает.

Что именно бот отбросил и почему — он пишет в ответе: строгий фильтр иногда
рубит настоящий заказ, а заметить это больше негде. Второй фильтр — кнопка
«🗑 Удалить» под каждым опубликованным объявлением.

### Снятие объявления с четырёх мест сразу

Обычная просьба автора — «нашли людей, уберите объявление». Одно объявление к
этому моменту висит **в четырёх местах**: карточка на сайте, пост в
Telegram-канале, пост в Threads и ролик в Instagram. Раньше кнопка убирала
только карточку, а остальные три поста продолжали приводить звонящих на
закрытую вакансию — и снимать их приходилось руками.

Теперь по кнопке снимается всё, что позволяют площадки, — поэтому и подпись у неё
теперь просто «🗑 Удалить», а не «Удалить с сайта» и не «Снять с доски»:

| Где | Кто снимает | Чем ограничено |
|---|---|---|
| Сайт | бот | — |
| Telegram-канал | бот | Telegram не даёт боту удалять свои сообщения старше **48 часов** |
| Threads | бот | своя норма — **100 удалений в сутки**, отдельно от нормы на публикации |
| Instagram | **админ, руками** | см. ниже |

Чтобы было что снимать, бот запоминает, куда объявление уехало:
`channel_message_id`, `threads_post_id` и `instagram_media_id` в
`imported_listings`. Приходят эти три числа вразнобой — пост в канале сразу при
публикации, Threads через минуты своей очереди, ролик ещё позже, — поэтому
`imports.setPosts` дописывает то, что стало известно, а не пишет все три поля
разом. Объявления, опубликованные **до** этой правки, постов за собой не
записали: у них кнопка снимет карточку с сайта и честно скажет, что остального
не знает.

**Почему Instagram — руками.** Удаление медиа у Meta есть (`DELETE
/{ig-media-id}`), но оно доступно только приложениям на **Facebook Login** с
разрешением `instagram_manage_contents`. Мы работаем через **Instagram Login**
(`graph.instagram.com`, см. `INSTAGRAM_GRAPH_HOST`), где этой операции нет
вовсе. Переезд на Facebook Login — это бизнес-аккаунт, привязанная
страница Facebook, повторная авторизация и App Review на новое разрешение;
ради одной кнопки это несоразмерно. Поэтому бот делает следующее лучшее: берёт
у Meta `permalink` ролика и даёт прямую ссылку на пост. В приложении это два
касания вместо поисков ролика в ленте.

Ни один отказ площадки не считается провалом всего снятия: с сайта объявление к
этому моменту уже убрано, и оборванный запрос к Meta не повод об этом молчать —
в отчёте будет строка о том, что именно не снялось и почему.

Команда `/stats` показывает, сколько объявлений опубликовано сегодня (день
считается по Бишкеку), сколько роликов ещё собирается или загружается на
площадки и сколько токенов разбора потрачено за сутки — в них упирается весь
поток объявлений, и больше их нигде не видно (подробнее ниже, в разделе про
лимиты). Те же строки бот присылает сам после каждой пачки.

Команда `/now` (или просто «выпусти», «выпускай», «публикуй») выпускает ролик
из того, что уже стоит в очереди, не дожидаясь расписания — хоть из одного
объявления. Ролик из одного объявления называется в единственном числе —
«Вакансия дня», а не «Вакансии дня». Если ролика ждут сразу несколько типов,
бот спросит кнопками, какой выпускать.

### Сколько роликов в сутки и почему не больше

Бот выкладывает **не больше десяти публикаций в сутки, по ролику примерно раз в
два с половиной часа, и до трёх объявлений в каждом ролике**
(`INSTAGRAM_DAILY_LIMIT`, `INSTAGRAM_RELEASE_MINUTES`, `BATCH_SIZE` в
`social/index.js`).

Так было не всегда. Сначала ролик ждал трёх объявлений одного типа — квоту
Instagram тратит пост, а не объявление, и тройка втрое поднимала пропускную
способность. У ожидания, однако, не было конца: тип, которого приходит по
одному в день, не доезжал вовсе. Тогда пачку убрали, ролик стал уходить сразу,
и потолок подняли до полусотни.

Это и оказалось ошибкой. Полсотни почти одинаковых роликов в сутки — поведение
не живого человека, а рассылки: один макет, один набор хештегов, один голос,
ровная очередь публикаций. Формально ничего не нарушено, но в рекомендации
такой аккаунт не попадает, и просмотров у роликов нет.

Теперь пачку держит не наполнение, а расписание: раз в два с половиной часа
выезжает то, что накопилось, — хоть одно объявление, хоть три. Объявлений в
ленту попадает столько же, сколько и раньше, а постов выходит 8–10 в сутки,
ровным потоком, а не залпом. Ничто при этом не ждёт компанию бесконечно: если
объявление простояло в очереди больше шести часов, оно из неё просто
выбрасывается — на сайте, в канале и в Threads оно к этому моменту уже есть.
Платной рекламы ни расписание, ни срок не касаются: она встаёт в голову очереди
и по сроку не выбрасывается.

Что расписание не лечит: трендовый звук через API подложить нельзя (аудио из
библиотеки Instagram выбирается только вручную в приложении), а ролик из
статичной карточки досматривают плохо. Если охват не вернётся за две-три недели
спокойного режима, смотреть надо туда — и в «Настройки → Статус аккаунта»,
где Instagram прямо пишет, годится ли контент для рекомендаций.

### Ролики для Instagram

Вместе с публикацией бот собирает вертикальный ролик 720×1280 на 9 секунд: сцена
с объявлением в фирменных цветах сайта и концовка «Шабашка.com — найди работу».
Плашка выезжает из-за края, заголовок и описание проявляются строка за строкой,
цена выскакивает и досчитывается до своей суммы, логотип сайта появляется в подвале
кадра, а красный круг из центра открывает концовку. Всё, что не служит чтению, —
медленное: наезд на кадр и два еле заметных пятна на фоне.

Каждый кадр рисуется на канвасе (`backend/src/social/card.js`) и уходит сырыми
пикселями в stdin ffmpeg — промежуточных картинок на диске нет. Верстка считается
в координатах 1080×1920 и масштабируется при выводе, поэтому разметку кадра можно
править в привычных цифрах. И канвас, и ffmpeg приезжают npm-пакетами — ставить
что-то в систему на Render не нужно.

Фоновая музыка берётся случайным файлом из `backend/assets/music/` — там лежат
десять инструменталов Kevin MacLeod под CC BY 4.0, нарезанных по 20 секунд.
Лицензия требует называть автора, поэтому строка о треке автоматически уходит
в описание поста, а файл без записи в `credits.json` бот не берёт вовсе (см.
README в самой папке). Пустая папка — ролик уходит с тишиной. Подложить трек
из библиотеки Instagram нельзя: аудио оттуда выбирается только вручную
в приложении, а ролик, опубликованный по API, уходит со своей дорожкой.

Картинку для сетки профиля Instagram берёт не с первого кадра, а с 3.6-й секунды
(`COVER_AT` в `card.js`, уходит в API как `thumb_offset`): к этому моменту объявление
нарисовано целиком, тогда как в начале ролика кадр ещё пустой. В сетке видно не весь
кадр, а 4:5 из его середины — по 285 точек сверху и снизу срезается, — поэтому блок
с объявлением начинается ниже, чем выглядело бы правильным в полном кадре.

Телефон на кадр не выносится: в ленте Instagram он остался бы навсегда и без ведома
владельца, тогда как на сайте живёт вместе с объявлением, которое можно закрыть.

Если заданы `INSTAGRAM_USER_ID` и `INSTAGRAM_ACCESS_TOKEN`, бот публикует ролик как
Reels сам; Instagram скачивает mp4 с бэкенда по временной ссылке `/api/social/video/…`,
поэтому адрес из `TELEGRAM_WEBHOOK_URL` должен быть доступен извне. Без этих переменных
(или если публикация не удалась) бот просто присылает готовый mp4 с подписью в чат —
остаётся выложить вручную.

Соединение до серверов Meta рвётся часто (`fetch failed`), и почти всегда тот же
запрос проходит со второй попытки. Поэтому запросы, которые ничего не публикуют —
создание контейнера и опрос статуса, — повторяются сами (`backend/src/social/net.js`,
три попытки с растущей паузой). Публикацию слепо повторять нельзя: если запрос
дошёл, а ответ потерялся, второй такой же выложит второй ролик — поэтому на сетевом
сбое бот сначала спрашивает у контейнера его статус и считает дело сделанным, если
там уже `PUBLISHED`.

Threads публикуется сразу и без очереди — одновременно с сайтом и
Telegram-каналом, а не после них. Пост текстовый, ему не нужен ни собранный
mp4, ни обработка на стороне Meta. Instagram идёт через отдельную очередь с
90-секундной паузой между роликами (см. ниже): ему нужен готовый mp4, а сборка и
обработка на стороне Meta занимают минуты. Ролик собирается прямо перед
Instagram — единственной площадкой, которой он нужен. Часовой лимит Graph API у
Instagram и Threads общий на всё приложение, но текстовый пост — это два-три
вызова против трёх десятков на Reels, так что Threads эту очередь и не ждёт: от
такой уступки Instagram ничего не теряет. Площадки друг от друга не зависят в
обе стороны: не собрался ролик — Threads всё равно опубликован, а «User is
performing too many actions» в Instagram не стоит текстового поста.

Когда попытки всё-таки не хватило, бот не ждёт, что админ нажмёт кнопку: пробует
сам с растущей паузой — 5, 10, 20, 30, 45 минут и дальше раз в час, всего почти
шесть часов (`backend/src/telegram/bot.js`, `AUTO_RETRY_DELAYS`). Пауза растёт не
для красоты: сетевой сбой проходит за минуты, а «too many actions» — это троттлинг
на часы, и частые попытки упираются в него же, попусту тратя лимит приложения.

Повторяемый шаг здесь не только публикация, но и **сборка ролика**: если она
сорвалась (обычно `fetch failed` на музыке или шрифте), объявление уже стоит на
сайте, в Telegram и в Threads — терять Instagram незачем, и повтор просто соберёт
mp4 заново. В отчёте это строка Instagram, а не отдельная ошибка: сорвавшаяся
сборка касается только его.
Собранный ролик двенадцать часов лежит в памяти процесса, так что обычный повтор
идёт без пересборки и только по тем площадкам, где не вышло (уже опубликованное
вторым постом не полезет). К сообщению об ошибке приходит ещё и кнопка 🔁
«Попробовать опубликовать ещё раз» — ей можно поторопить бота, не дожидаясь паузы.
Если не помогло за все шесть часов или процесс перезапустился, бот честно говорит,
что дальше только руками из сообщения выше.

Отдельный случай — **упор в суточную норму** Instagram или в антиспам Threads.
Пятиминутными попытками его не пройти: окно у Meta скользящее, место освобождается
ровно через сутки после занявшей его публикации. Раньше каскад на этом
останавливался совсем, и ролик ждал, пока админ вспомнит про кнопку. Теперь бот
обнуляет расписание и возвращается к ролику **через десять часов**
(`LIMIT_RETRY_DELAY_MS`), а потом, если норма всё ещё занята, ещё через десять —
дальше уже только кнопкой. Об этом он пишет в чат сразу, чтобы объявление не
выглядело потерянным.

### Карточка платной рекламы

Реклама с припиской `/ad` публикуется как есть, но **раздел ей выбирается такой
же, как всем**: вакансию надо положить в вакансии, разовый заказ — в заказы, и
только остальное (школа языков, курсы, салон, магазин) — на доску. Поэтому текст
всё-таки показывается модели: контент она не трогает — ролик и макет уходят
ровно такими, какими их прислали, — а по подписи говорит тип и заодно разбирает
город, категорию и зарплату.

Описание при этом всегда своё, из присланного текста. Модель возвращает список,
и в одной рекламе кофейни она видит три вакансии сразу — бариста, техничка,
повара. Взять описание у первой значило бы выбросить из оплаченного объявления
две трети.

Когда модель не ответила (не влезло, кончился суточный лимит), тип берётся по
словам: «требуются» плюс разговор про зарплату, оплату, график или смену —
вакансия, иначе доска. Признаки нужны оба сразу: ошибиться типом у оплаченной
рекламы так же некрасиво, как свалить её на доску. Заголовок в этом случае
собирается не из одной первой строки — «Требуются:» на карточке и в ролике не
говорит ничего, — а из первой и второй сразу, со снятыми эмодзи: «Требуются:
Бариста с опытом работы».

**`/ad_fast` — реклама вообще без разбора.** «Вне очереди» помогает не всегда:
дорожки Groq общие, и когда выбран суточный лимит, первое место в очереди
ничего не решает — реклама откладывается вместе со всеми и ждёт часами. В ночь
на 7 сентября объявление кофейни так простояло пять минут на двух подходах и
ушло в отложенные до часа ночи. По команде `/ad_fast` (можно `/adfast`, можно
отдельным сообщением, как `/ad`) к модели не идут вовсе: объявление уходит на
сайт, в канал, в Threads и роликом в Instagram в ту же секунду. Платим за это
разбором — города, категории и зарплаты в карточке не будет, их называет
модель. Тип берётся по словам, заголовок из первых строк (см. выше).

Промежутки между постами команда не снимает: десять минут в Threads держат
антиспам (подкод 2207051 — блокировка на часы, повтором не снимается), полторы
минуты в Instagram — часовой лимит Meta. Обгонять их нельзя никому, и «быстро»
здесь означает «без ожидания разбора», а не «мимо площадочных пауз». А вот свой
суточный потолок (`INSTAGRAM_DAILY_LIMIT`, по умолчанию 10) рекламу не держит:
за неё заплатили, и ждать сутки она не должна. Обычные объявления на этом
потолке останавливаются, реклама идёт дальше — до настоящей нормы Meta (100).
Если занята и она, ролик всё равно собирается и приходит в чат готовым mp4
(`buildForHand`, см. ниже).

Набирать команду заново, когда реклама уже уехала в отложенные, не нужно:
к сообщению «⏳ Лимиты разбора выбраны» прикладывается кнопка **⚡ «Выложить
сразу, без разбора»**. Она снимает таймер возврата и публикует то же самое
объявление тем же путём — текст у бота уже есть. Нажатие второй раз ничего не
делает: если бот успел вернуться к объявлению сам, кнопка отвечает об этом и
второй карточки не создаёт.

Чаще всего до кнопки теперь не доходит: **под рекламу отложена целая модель**.
Норма у бесплатного Groq — около сорока разборов в день на модель, и тратит её
в основном поток из чужих групп, который идёт весь день и никого не ждёт.
Реклама же приходит когда придёт, часто вечером, и упиралась в пустую норму.
Последняя ступень лесенки моделей (см. «Лесенка моделей») постам из групп не
достаётся вовсе: когда они выберут все остальные, реклама и пересланное
админом по-прежнему разбираются. В `/stats` это видно строкой «Обычные модели
выбраны».

Раньше запас считался токенами — и не работал: счётчик жил в памяти процесса,
Render перезапускал сервис, и бот думал, что потрачено почти ничего, пока Groq
отвечал «Used 199145 из 200000». Выбранность модели бот теперь узнаёт из
отказов самого Groq, и перезапуск её не сбрасывает в неправду.

Если лимиты не отпустили и за все шесть заходов, реклама всё равно выходит —
как есть, без разбора: заплатили за публикацию, а не за разбор. Обычное
объявление в этом случае, как и раньше, придётся прислать заново.

**Отложенное переживает перезапуск.** Раньше оно жило только в памяти процесса,
и рассуждение было такое: «доразбор через сутки после падения всё равно никому
не нужен». Для постов из групп это верно, а для платной рекламы — нет.
Бесплатный Render перезапускает сервис сам: по нехватке памяти, при выкате,
после сна, — и вместе с процессом исчезали и таймер, и текст объявления.
В чате при этом оставалось бодрое «⏳ вернусь к нему сам через ≈ 7 мин», за
которым не приходило уже ничего. Именно так однажды «потерялось» объявление на
три вакансии.

Теперь отложенная реклама лежит в таблице `deferred_parses` (см.
`telegram/deferred.js`): строка на объявление, которую бот убирает, когда до
него дошли руки или когда его выложили кнопкой. При запуске бот читает их
обратно, ставит на тот же срок, который назвала модель, и пишет в чат
«♻️ Сервер перезапускался. Отложенных объявлений не потерял: N». Протухшее
(старше 12 часов) не воскрешает: объявление суточной давности — уже не
объявление.

**Обратный слэш из объявления.** В кыргызстанских объявлениях он стоит через
раз: «2300-2600 с\смена», «график 2\2, 3\1, 5\2». Модель переписывает текст
слово в слово, и в JSON попадает одиночный `\с` — недопустимая
escape-последовательность, на которой `JSON.parse` валит **весь ответ целиком**.
В ночь на 7 сентября так потерялась разобранная реклама кофейни: в чат пришло
«Разобрать не вышло: Bad escaped character in JSON», и объявление ушло на доску
запасным путём. Просить модель экранировать бесполезно — она копирует текст, как
видит. Поэтому ответ чинится на месте (`repairJson` в `extract.js`): одиночные
слэши удваиваются, живые переводы строк внутри строки экранируются. Правильный
ответ при этом не трогается — починка включается только после неудачного разбора.

Платная реклама ждать десять часов не обязана, поэтому для неё ролик собирается
**даже когда публиковать его некуда** (`buildForHand` в `social/index.js`): mp4
приходит в чат вместе с отчётом, и рекламу можно выложить руками из приложения
прямо сейчас. Раньше до сборки в этом случае не доходило вовсе — квота
проверяется до неё, — и в чат приходила одна строка об отказе, без файла. Для
обычных объявлений так не делается: минута ffmpeg на бесплатном Render ради
ролика, которого никто не просил, того не стоит. Если реклама пришла своим
файлом (готовый ролик, макет), собирать нечего — он у админа и так есть, поэтому
бот присылает только готовую подпись со ссылкой и хештегами, чтобы не набирать
её заново.

### Пост в Threads

С `THREADS_USER_ID` и `THREADS_ACCESS_TOKEN` то же объявление уходит ещё и в
Threads (`backend/src/social/threads.js`). Обычное объявление — **текстом, без
ролика**: так лента и набирает свои просмотры (за сентябрь 2026 — почти два
миллиона за тридцать дней, 98% из них — не подписчики), и менять работающее
незачем. API отдельное от инстаграмного: свой хост `graph.threads.net`, свой ID
профиля и свой токен, даже если аккаунт заведён на том же Instagram. Площадки
работают независимо: протухший токен Instagram не мешает посту в Threads и
наоборот, а в чат приходит строка о каждой.

**Тег темы — отдельным полем.** Тег у Threads один на пост: из хештегов в конце
текста тегом становился только первый, «шабашка», а остальные оставались
просто словами с решёткой — «шабашка #вакансиибишкек #жумуш» — и занимали место
у описания. Теперь тег уходит полем `topic_tag` (`THREADS_TOPIC_TAG`, по
умолчанию тот же «шабашка»), а текст остаётся чистым.

Готовность контейнера всё равно спрашивается, хотя кодировать в текстовом посте
нечего: Meta просит дождаться её у любого контейнера и на попытку опубликовать
раньше отвечает «An unknown error occurred» — то есть ничем. Фиксированной паузы
нет, вместо неё опрос статуса: текст обычно готов сразу, так что в норме это один
лишний вызов. Не ответил и статус — публикуем всё равно: отказаться от поста из-за
неудачной проверки было бы хуже.

Отдельная история — **коды ошибок Meta**. Коды 1 (`API Unknown`) и 2
(`API Service`) она сама называет временными, и наружу они выходят той же строкой
«An unknown error occurred»; такие повторяются наравне с сетевым сбоем
(`isTransientApiError` в `net.js`). Остальные уходят наверх сразу — протухший
токен от повтора не оживёт, а попытка потратит вызов из часового лимита. В
сообщении об ошибке всегда есть шаг, код и `fbtrace_id`: по одной строке от Meta
не понять ни этапа, ни причины, а трейс — единственное, по чему её поддержка
найдёт конкретный запрос.

Текст поста собирается свой (`threadsText` в `video.js`), и причина не только в
лимите 500 знаков (эмодзи там считаются байтами UTF-8, поэтому и меряем так же).
Threads, в отличие от Instagram, делает ссылки кликабельными — значит, в пост идёт
прямой адрес объявления, а не приглашение в шапку профиля. Сначала собирается
обязательное — заголовок и ссылка, — а описание ужимается под остаток и режется по
словам. Указания автора трека здесь нет: музыка живёт в ролике, а ролика в этом
посте не будет.

Публиковать можно не больше 250 постов в сутки на профиль; при нынешнем потоке
объявлений до этого далеко.

### Реклама в Threads

Рекламу у Шабашки заказывают именно в Threads, и в шапке профиля обещано:
«50 сом — гарантированно 1000+ просмотров за 24 часа». Средний пост ленты
набирает около тысячи — то есть гарантия стоит ровно на середине, и часть реклам
до неё не дотягивает. Поэтому у рекламы в Threads своя дорога:

- **Пометка — по желанию.** По умолчанию реклама выходит тем же видом, что и
  обычные объявления: так решил владелец. `AD_LABEL=Реклама` добавит первой
  строкой «📣 Реклама» — в Threads, в канале и в подписи Instagram. Стоит
  помнить, что правила Meta требуют отмечать оплаченное продвижение, а закон о
  рекламе — делать её узнаваемой.
- **Картинка.** Реклама без своего файла уходит карточкой объявления — картинку
  в ленте замечают раньше текста (`THREADS_CARDS`). Реклама со своим файлом —
  **самим файлом**: раньше в Threads уходила одна подпись, а ролик или макет
  рекламодателя туда не попадали вовсе. Не прошла картинка — пост уходит
  текстом: реклама без картинки лучше, чем реклама, которой нет.
- **Длина.** Подпись к рекламе бывает на тысячу знаков, а Threads берёт
  пятьсот, и такой пост он просто отбивал. Теперь описание режется по словам,
  а пометка и ссылка на карточку остаются целыми (`threadsCaption` в `video.js`).
- **Свой ролик в Instagram.** Реклама не ждёт расписания и не делит ролик с
  обычными объявлениями — рекламодатель платит за свой пост.

**Бот следит за просмотрами** (`backend/src/social/adTracker.js`, таблицы
`ad_campaigns` и `ad_posts`). Через шесть часов (`AD_WARN_HOURS`) он смотрит
статистику поста, и если реклама набрала меньше шести десятых обещанного —
пишет об этом с кнопкой **🔁 «Поднять в Threads»**: реклама выходит ещё раз тем
же постом (файл рекламодателя бот заново берёт из Telegram по `file_id`), и
просмотры складываются. Поднимать можно до двух раз. Через сутки приходит
отчёт — просмотры, лайки, ответы, репосты и выполнена ли гарантия, — сделанный
так, чтобы его можно было переслать рекламодателю как есть. Кампании живут в
базе, а не в памяти: сутки без перезапуска на бесплатном Render не проживает
ничто.

`/ads` — реклама за три дня с числами и кнопками отчёта по каждой; `/threads` —
статистика аккаунта за сутки и неделю и сколько в среднем набирает один пост.
Этими числами удобно отвечать тем, кто спрашивает про рекламу.

**Заявки из ответов** (`backend/src/social/leads.js`). Раз в полчаса бот
просматривает ответы под последними постами и под рекламой за двое суток и
присылает только те, где спрашивают про рекламу: «сколько стоит разместить»,
«прайс», «жарнама». Вопросы про вакансии («номер?», «сколько платят?») не
присылает — их десятки в день. Личные сообщения Threads через API не отдаёт,
их смотреть по-прежнему в приложении.

Для статистики нужно разрешение `threads_manage_insights`, для ответов —
`threads_read_replies`. Если у токена их нет, бот скажет об этом один раз и
дальше не будет тратить вызовы.

### Токены продлеваются сами

Токены Threads и Instagram (Instagram Login) живут шестьдесят дней и
продлеваются одним запросом — но только пока живы: истёкший придётся получать
заново руками. А без токена Threads встал бы весь рекламный канал, и встал бы
молча. Поэтому бот продлевает их сам раз в неделю (`backend/src/social/tokens.js`)
и хранит продлённый токен в таблице `app_settings`: переменную окружения на
Render изнутри приложения не поменять. Если вписать в Render новый токен, бот
заметит это по отпечатку и начнёт с него. Сам токен не попадает ни в лог, ни в
сообщения. Не продлился — бот пишет в чат, сколько дней осталось.

### Автоимпорт из канала-источника (без пересылки руками)

Всё, что описано выше, публикуется само в момент, когда админ прислал боту
переслал сообщение. Последнее ручное звено — сама пересылка. Если
вакансии постоянно берутся из одного чужого Telegram-канала (админ там просто
подписчик, не владелец), это звено тоже можно снять: `sourceWatcher.js` сам
следит за новыми постами канала и отдаёт их в тот же разбор и ту же публикацию,
что и пересланные сообщения — очередь, дедуп по телефону+заголовку, отчёт в чат,
повторные попытки соцсетей, всё общее.

**Почему юзер-сессия, а не бот.** Telegram Bot API отдаёт посты канала боту,
только если бот сам — администратор этого канала. Чужим каналом это не
устроить (владелец не пустит туда бота), поэтому здесь MTProto-клиент
([GramJS](https://gram.js.org/)) — по сути тот же Telegram, что открыт на
телефоне, только без интерфейса, под тем аккаунтом, который на канал уже
подписан.

**Настройка (один раз):**

1. Зайти на [my.telegram.org](https://my.telegram.org) → *API development
   tools* тем аккаунтом, который подписан на канал-источник. Получить
   `api_id` и `api_hash`, вписать в `backend/.env` как `TELEGRAM_API_ID` и
   `TELEGRAM_API_HASH`.
2. Из папки `backend` выполнить `npm run telegram-login` — скрипт спросит
   номер телефона, код из Telegram (и пароль двухфакторной аутентификации,
   если она включена) и выведет строку `TELEGRAM_SESSION_STRING=...`.
   Вписать её в `backend/.env` (и в переменные окружения сервиса на Render).
   Значение секретное: оно равносильно входу в аккаунт с нового устройства.
3. Задать `SOURCE_CHANNEL` — `@username` канала или его числовой id, через
   запятую, если источников несколько. Аккаунт, под которым получена сессия,
   должен быть подписан на каждый из них: иначе Telegram не отдаст историю, и в
   логе появится «не смог открыть "…"».
4. Перезапустить бэкенд — в логе должна появиться строка «Автоимпорт из
   канала включён: …».

**Фильтр по типу.** `SOURCE_LISTING_TYPE` решает, что из источника публиковать.
По умолчанию `all` — всё, кроме явного мусора (`other`). Сузить можно списком
через запятую, но помнить надо вот что: **фильтр стоит после модели**. Разбор
за отброшенный тип уже оплачен из суточной нормы токенов, и на ней это видно
сразу. Раньше здесь стояло `vacancy,order`, и каждое объявление с доски —
«продаю», «сдаю», «делаем ремонт под ключ», реклама курсов или школы — уходило
в мусор уже разобранным. Такому объявлению на сайте место есть (доска), а
заплатили мы за него столько же, сколько за вакансию.

**Что отсеивается до Groq.** Суточная норма — около 43 разборов на аккаунт, а
рекламный чат за вечер даёт сотню сообщений. Поэтому до модели доходит не всё:

- второе и последующие фото одного поста (`grouped_id`) — текст объявления
  Telegram кладёт только в первое сообщение альбома, остальные дали бы лишние
  вызовы и дубли карточек на сайте;
- посты без текста — картинки мы не читаем, и объявление, нарисованное на
  фотографии, проходит мимо. Это осознанный размен: в этих группах пишут
  текстом, а картинка стоила бы вдвое дороже разбора;
- текст короче 15 символов («+», «салам») — объявлением он быть не может;
- текст без телефона — такое объявление всё равно не публикуется (откликнуться
  некуда), это видно по `handleParsed` в `bot.js`, так что разбор был бы
  выброшен впустую;
- посты старше `SOURCE_MAX_AGE_HOURS` (по умолчанию 12 часов) — проверка стоит
  перед самым разбором, а не при приёме: пока пост стоял в очереди, он мог и
  устареть.

По длине очередь не обрезается специально: вакансия, написанная утром, вечером
всё ещё живая, и выбрасывать её только потому, что перед ней стоят другие, —
потеря на ровном месте, она бы дождалась. Порог по возрасту заодно страхует от
бесконечного роста очереди: если из групп приходит больше, чем Groq успевает
разбирать, отставание упирается в этот порог и дальше не растёт — протухшая
голова очереди отбрасывается мгновенно, без запроса к модели.

**Подпись под фото — это и есть объявление.** В рекламных чатах текст пишут
подписью к картинке. Если в подписи есть телефон и она достаточно длинная, пост
разбирается как текст: это примерно втрое дешевле по минутному лимиту и точнее,
чем читать тот же текст с фотографии. Иначе разбирается картинка, и подпись
уходит модели вместе с ней — помеченная как данные, а не как указания (текст из
чужого чата доверия не заслуживает).

**Очередь двухуровневая.** Скриншот, присланный админом руками, — это человек,
который ждёт ответа; поток из чужих групп подождёт. Поэтому посты из источников
встают в хвост очереди, а присланное руками — перед первым фоновым. Без этого
один разговорчивый чат забивал бы очередь на полчаса вперёд.

**Куда приходит отчёт.** Публикация из канала идёт тем же путём, что и
объявление, — значит, будет и то же сообщение в Telegram: карточка, кнопка
«🗑 Удалить», статус по Threads/Instagram. По умолчанию оно уходит первому
из `TELEGRAM_ADMIN_IDS`; отдельный чат можно задать через
`SOURCE_REPORT_CHAT_ID`.

**Ограничение бесплатного Render.** Юзер-сессия держит постоянное соединение,
и на бесплатном тарифе оно обрывается, когда Render усыпляет сервис (см.
«Сон бесплатного Render» ниже) — самопинг покрывает почти сутки (5:00–1:00 по
Бишкеку), но не все 24 часа. Посты канала в это окно будут пропущены. Для
круглосуточной работы нужен платный тариф Render ($7) — там сервис не спит
вовсе.

У Groq бесплатный тариф без карты и без региональных ограничений (в отличие
от Gemini, который в Кыргызстане выдаёт нулевую квоту): 1000 запросов в сутки —
для одного бота с ручной модерацией этого хватает с запасом, платить не нужно.

Лимитов у Groq два, и путать их нельзя:

| | сколько | видно ли |
|---|---|---|
| в минуту | 8000 токенов | да, в заголовках `x-ratelimit-*` каждого ответа |
| в сутки | 200 000 токенов и 1000 запросов | **нет** — Groq их не присылает |

Оба считаются **на организацию**, а не на ключ: второй ключ того же аккаунта
общий лимит не поднимает, второй аккаунт — поднимает вдвое. Ключи вписываются
в `GROQ_API_KEY` через запятую, очередь (`backend/src/telegram/queue.js`) сама
разбирает по одному объявлению на ключ параллельно.

Минутный лимит держится сам: Groq присылает остаток в заголовках, по ним и
считается пауза — при свободном лимите её нет вовсе, а если лимит выбран,
запрос повторяется через время, названное самим Groq в ответе 429.

А вот суточный не виден ниоткуда, и упирается поток объявлений именно в него.
Поэтому бот считает расход сам (`spend` в `extract.js`, число берётся из
`usage.total_tokens` каждого ответа) и показывает его в `/stats` строкой
«🧠 Разборов: 24, токенов ≈180к из 400к». Когда лимит всё-таки выбран, поток из
групп встаёт, и раньше это выглядело как тишина в чате: ошибка фоновой задачи
уходила в лог Render, а в Telegram не приходило ничего. Теперь бот пишет об
этом один раз в сутки и называет срок, если Groq его назвал.

Из чего складывается один запрос:

| | токенов |
|---|---|
| системный промпт | ≈2500 |
| само объявление | 100–900 |
| потолок ответа | сколько запросили — Groq резервирует его заранее, ещё до ответа |
| **итого** | **≈4500 из 8000 в минуту, то есть ~43 разбора в сутки на аккаунт** |

Раньше выходило вдвое дороже — 7800 на разбор и 26 объявлений в сутки. Съедали
картинки: скриншот стоил ровно 2048 токенов независимо от размера, и правила
про ленту чата в промпте были нужны только ему. От чтения картинок отказались
(объявления в этих чатах пишут текстом), а промпт после этого ужался с 4255
токенов до 2500 — правила остались все, вырезаны повторы и объяснения.

Потолок ответа — 2000, и если запрос всё-таки не влез, повтор идёт с 1200 и
800 (`TEXT_STEPS`). Запрос, отбитый по размеру, до модели не доходит и лимит не
тратит — поэтому паузу между такими повторами бот не держит.

Сменой модели минутный лимит не поднять: у `qwen`, `gpt-oss-120b` и
`gpt-oss-20b` он одинаковый. Исключение — `groq/compound`: 70K в минуту вместо
8K, но всего 250 запросов в сутки и внутри свой веб-поиск. Пробуется через
`GROQ_MODELS` без правки кода. Зрение при выборе модели больше не
требуется — картинок мы не шлём.

### Лесенка моделей

Суточная норма у Groq считается **отдельно на каждую модель** — в отказе так и
написано: «Rate limit reached for model qwen/… … on tokens per day (TPD)».
Раньше бот знал одну модель и, выбрав её двести тысяч токенов, стоял до утра, а
вместе с ним и реклама: вечером 25 сентября оба ключа показывали «Used 199145
из 200000», а нормы других моделей на тех же ключах лежали нетронутыми.

Теперь моделей несколько (`GROQ_MODELS`), и бот спускается по ним: сначала
лучшая модель на всех ключах, потом следующая. Выбранную модель он помнит до
срока, который назвал Groq («try again in 11m15s» — норма у него скользящая, а не
до полуночи), и лишних запросов к ней не делает. Последняя ступень — резерв под
рекламу. Что сейчас с каждой моделью, видно в `/stats`.

У разных моделей и размышления выключаются по-разному: qwen понимает
`reasoning_effort: none`, gpt-oss выключить их не даёт и получает `low`, а llama
этого поля не знает вовсе и на него отвечает 400 — ей его не шлём.

**Не «слишком большое объявление».** Когда до конца суточной нормы остаётся
меньше, чем просит разбор, Groq отвечает 413 «Request too large … (TPD)». Бот
принимал это за слишком длинный текст: урезал потолок ответа, пробовал снова и
в конце концов терял объявление с ошибкой про «минутный лимит» — в логах Render
за один вечер набралось полсотни таких «не влез» на сообщениях в две строки.
Теперь отказ с «per day» считается выбранной нормой, и разбор уходит на
следующую модель.

**Модель пропала.** Qwen у Groq в разделе preview, а такие модели он снимает без
предупреждения и даже без записи на [странице устаревших](https://console.groq.com/docs/deprecations).
Так в сентябре 2026 пропала `qwen/qwen3.6-27b`: на каждое объявление Groq
отвечал «model does not exist», и шесть часов из групп не выходило ничего.
Теперь пропавшую модель бот вычёркивает из лесенки и пишет админу, на какой
разбирает дальше.

Ошибки разбора объявлений из групп раньше писались только в лог Render. Теперь
бот говорит о них в чат — не чаще раза в час, пока ошибка повторяется.

Длинные ответы бот делит на несколько сообщений: больше 4096 знаков Telegram не
принимает (см. `splitText` в `backend/src/telegram/api.js`).

### Запасной шлюз

Второй способ обойти минутный лимит — подключить другой сервис и отдавать ему
перелив. Подойдёт любой, кто говорит в формате OpenAI chat completions:

```
FALLBACK_API_URL=http://localhost:20128/v1
FALLBACK_MODEL=<название модели на том шлюзе>
FALLBACK_API_KEY=<ключ; локальному OmniRoute не нужен>
```

Адрес можно писать и без `/v1`, и сразу с `/v1/chat/completions` — недостающее
дописывается само.

Groq при этом остаётся основным: он проверен на кыргызском и русском тексте с
фотографий, а бесплатные модели на чужих шлюзах по этой части очень разные.
Запасной включается только тогда, когда ждать пришлось бы по-настоящему — ни у
одного ключа Groq не осталось минутного лимита (см. `pickLane` в
`backend/src/telegram/extract.js`). Если запасной шлюз не ответил (модель сняли,
квота кончилась, туннель отвалился), объявление не теряется: разбор возвращается
на Groq и просто ждёт его лимита, как раньше.

Модель на запасном шлюзе должна уметь картинки — иначе посты с фотографиями
разберутся мусором. Прежде чем оставлять её включённой, стоит прогнать через
боту несколько настоящих объявлений и посмотреть, что она вернула.

**OmniRoute отдельно.** Он не облачный, а self-hosted: `npx omniroute` поднимает
шлюз на вашем компьютере (по умолчанию порт 20128). Бэкенд живёт на Render, и
`localhost` с вашей машины оттуда недоступен — значит, либо шлюз должен смотреть
наружу через туннель и компьютер быть включённым всегда, либо OmniRoute надо
поднимать отдельным сервисом рядом с бэкендом. Для круглосуточного бота проще
взять ключ у самого провайдера (у OmniRoute бесплатные модели — это чужие
бесплатные тарифы: Gemini, Cerebras, NVIDIA, Cloudflare) и вписать его адрес в
`FALLBACK_API_URL` напрямую, без шлюза посередине.

Свой Telegram ID бот подскажет сам — напишите ему что угодно, пока вас нет в
списке, и он ответит номером.

Без `TELEGRAM_WEBHOOK_URL` бот работает через long polling — это режим для
локальной разработки. В проде нужен именно вебхук: Render на бесплатном тарифе
засыпает без входящих запросов, и опрос Telegram обрывается, а входящий POST от
вебхука сервис будит.

## Деплой: бесплатный вариант без риска потерять базу

Три сервиса, каждый с бесплатным тарифом:

1. **Neon** или **Supabase** — Postgres. Создайте проект, скопируйте строку подключения
   (`DATABASE_URL`) — она не меняется даже при переходе на платный тариф в будущем.
2. **Render** — бэкенд (Node/Express). Подключите репозиторий, Render подхватит
   `render.yaml` (папка `backend`, `npm install` / `npm start`). В настройках сервиса
   на Render вручную впишите переменные окружения `DATABASE_URL` (из Neon/Supabase) и
   `PUBLIC_URL` (адрес фронтенда на Netlify, после его создания). `JWT_SECRET`
   сгенерируется автоматически. Домен у сайта кириллический, поэтому в `PUBLIC_URL`
   он записан в punycode-виде (`https://xn--80aaac0cyed.com`) — иначе его не поймут
   ни DNS, ни часть библиотек. В текстах объявлений бот разворачивает его обратно
   и показывает читаемое `шабашка.com/orders/131`.
3. **Netlify** — фронтенд (React/Vite). Подключите репозиторий, Netlify подхватит
   `netlify.toml` (сборка из папки `frontend`). В настройках сайта добавьте переменную
   окружения `VITE_API_URL`, указывающую на бэкенд на Render, например
   `https://shabashka-backend.onrender.com/api`.

Почему так: на бесплатном Render нет постоянного диска — при каждом перезапуске
файловая БД обнулялась бы. Neon/Supabase хранят данные отдельно и не зависят от
перезапусков бэкенда.

### Сон бесплатного Render

Render усыпляет бесплатный сервис после **15 минут** без входящих запросов, и
первый посетитель после простоя ждёт 30–50 секунд, пока контейнер поднимется.
Против этого работают три вещи:

1. **Самопинг** (`backend/src/keepalive.js`). Сервис раз в 12 минут дёргает свой
   же `/api/health` по адресу из `RENDER_EXTERNAL_URL` — таймер Render не
   успевает дойти до пятнадцати минут. Разбудить себя так нельзя: у спящего
   процесса таймеров нет, — это защита от засыпания, а не от сна.
   Круглые сутки не пингуем: в бесплатном плане 750 часов работы в месяц, а в
   месяце 744 часа, то есть запаса не остаётся вовсе. Поэтому окно — с 5:00 до
   1:00 по Бишкеку (`KEEPALIVE_FROM_HOUR` / `KEEPALIVE_TO_HOUR`): ~620 часов в
   месяц, и это те часы, когда на сайт реально заходят. Ночью сервис спит.
2. **Внешний пинг** — на случай, когда сервис всё-таки уснул (перезапуск, сбой
   сети): бесплатный монитор (cron-job.org, UptimeRobot) на
   `https://…onrender.com/api/health` с интервалом 10 минут. Только его расписание
   тоже стоит ограничить теми же часами, иначе 750 часов кончатся до конца месяца.
3. **Баннер «сервер просыпается»** (`frontend/src/components/WakingBanner.jsx`).
   Первый заход всё равно когда-нибудь окажется холодным, и пустой скелет на
   полминуты читается как «сайт сломан». `api.js` считает незакрытые запросы,
   и если ответа нет 5 секунд — сверху появляется объяснение.

Когда трафик вырастет, честное решение — платный тариф Render ($7): он не спит
вовсе, и вместе со сном уходит ограничение в 750 часов. Кроме скорости первого
захода это лечит и `robots.txt` с `sitemap.xml`: Netlify проксирует их на Render
и ждёт ответа около 26 секунд — на холодном старте поисковик получает ошибку.

### Что делает бот, когда что-то зависло

Три места, где молчание бота выглядело одинаково, а причины были разные.

**Запросы наружу без срока.** У `fetch` в Node своего таймаута нет: соединение,
оборванное без закрытия, висит, пока его не закроет та сторона. Разбор идёт из
очереди по одной дорожке на ключ Groq — и один такой запрос останавливал весь
поток объявлений молча. Теперь срок есть у всего: минута у Groq и у Telegram
Bot API, полторы минуты у Graph API Meta, три минуты на заливку ролика и
скачивание присланного файла, двадцать секунд у писем. Превышенный срок
считается сетевым сбоем — то есть его можно повторить, и запрос уходит на
следующую дорожку.

**Сторож очереди.** Если задача всё-таки не закончилась за десять минут,
очередь отбирает у неё дорожку и идёт дальше (`JOB_TIMEOUT_MS` в
`telegram/queue.js`). Помешать самой задаче мы не можем, но останавливать
из-за неё всё остальное — хуже. В `/stats` при этом появляется строка
«⚠️ Зависших разборов»: молчащий бот и бот, упёршийся в лимиты, снаружи
выглядят одинаково, а лечатся по-разному.

**Упавшая задача.** Node с пятнадцатой версии убивает процесс за необработанный
промис, так что одна ошибка в разборе могла отправить в перезапуск весь
бэкенд — вместе с сайтом. Очередь теперь ловит такое сама и пишет в лог.

## Планы на мобильное приложение

Бэкенд — чистый REST API с JWT (без сессий/cookie), поэтому его можно напрямую
подключить к будущему приложению на React Native: авторизация, список заказов,
публикация заказа и переход в WhatsApp работают без каких-либо изменений на сервере.
