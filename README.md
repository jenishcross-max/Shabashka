# Шабашка

Доска объявлений для поиска подработки и мастеров в Кыргызстане.

- **Заказчики** регистрируются (по email) и размещают заказы.
- **Исполнители** ничего не регистрируют — они просто смотрят заказы и пишут заказчику
  напрямую в WhatsApp кнопкой на странице заказа.
- Есть **вакансии** (постоянная/частичная работа) — параллельно с разовыми заказами.
- Есть **админ-панель** для модерации (пользователи, заказы, вакансии, жалобы, категории).

Архитектура сделана как REST API + отдельный веб-фронтенд, чтобы тот же бэкенд
можно было потом переиспользовать для мобильного приложения на React Native.

## Стек

- **backend/** — Node.js, Express, PostgreSQL (`pg`, для Neon/Supabase), JWT-авторизация
- **frontend/** — React (Vite), React Router

## Возможности

- Регистрация/вход заказчиков по email, отдельный номер WhatsApp для связи
- Публикация заказов и вакансий: категория, город, примерный адрес, бюджет/зарплата
- Лента заказов/вакансий: поиск, фильтры, сортировка, пагинация
- Просмотры, закреплённые ("🔥 Топ") объявления
- Избранное — работает без регистрации, хранится в `localStorage` браузера
- Редактирование/закрытие/удаление своих объявлений
- Жалобы на заказы, вакансии и записки с доски ("Пожаловаться") — без регистрации
- Админ-панель: статистика, пользователи (блокировка), заказы/вакансии (скрыть/закрепить),
  жалобы (модерация), категории (добавление/удаление)

## Что защищает площадку от ответственности за чужой обман

Сайт — посредник: объявления пишут пользователи, сделки идут вне сервиса. Посредник
не отвечает за чужой контент, пока он не знал о нарушении, убрал его после того как
узнал, и не выдавал чужое объявление за проверенное им самим. Всё, что для этого нужно
в коде, собрано в четырёх местах.

**Кнопка «Пожаловаться» на всём.** Была только у заказов — теперь есть у вакансий и у
записок на доске (`POST /api/{orders,vacancies,board}/:id/report`, все три без
авторизации: обманывают обычно исполнителя, а он на сайте не регистрируется). Жалоба
одновременно уходит в Telegram админам — см. `telegram/notify.js`. Ждать, пока кто-то
зайдёт в админку, нельзя: вся защита в том, что нарушение убрали быстро.

**Жалоба переживает объявление.** Раньше `reports` ссылалась на `orders(id) ON DELETE
CASCADE`, и после удаления заказа от разбора не оставалось ничего. Теперь ссылка
полиморфная (`listing_type`/`listing_id`, как в `conversations`), без внешнего ключа, и
вместе с жалобой сохраняется `snapshot` — копия объявления на момент подачи. Пока
жалобу разбирают, автор успевает поправить текст, а записка на доске вообще живёт
сутки.

**Журнал модерации** (`moderation_log`, см. `moderation.js`). Всё, что снимают с сайта —
из админки или кнопкой в боте, — уходит туда вместе с полной копией строки. Это
единственный способ ответить на вопрос «что там было написано и как быстро вы это
убрали» после удаления. Заказ и вакансию по жалобе не удаляем, а закрываем, записку на
доске — скрываем (`hidden`): объявление с жалобой само себе доказательство.

**Пометка импортированных объявлений** (`is_imported` у orders, vacancies, board_posts).
Бот публикует чужие объявления от имени администратора, и без пометки это выглядит как
объявление, поданное на сайт и кем-то проверенное — ровно та подмена, из-за которой
площадка перестаёт быть посредником. На карточке стоит «Объявление взято из открытых
чатов. Автора мы не проверяли», на доске — «ℹ️ Из открытых чатов». Рядом с телефоном
в любом объявлении — предупреждение про предоплату (`SafetyNote.jsx`): почти все истории
«меня обманули» начинаются с перевода вперёд.

Всё это описано и в «Условиях использования» (`frontend/src/pages/Terms.jsx`): роль
сервиса, отсутствие проверки авторов, объявления из открытых источников и порядок
удаления по просьбе автора, порядок работы с жалобами.

> Это не юридическая консультация. Как перечисленное выглядит по законам КР и нужна ли
> регистрация ИП/ОсОО для площадки с объявлениями — вопрос к юристу, а не к README.

## Локальный запуск

```bash
npm run install:all
```

Нужна база Postgres (можно бесплатный проект на [Neon](https://neon.tech) или
[Supabase](https://supabase.com) — см. раздел про деплой ниже). Скопируйте
`backend/.env.example` в `backend/.env`, впишите `DATABASE_URL` и свой `JWT_SECRET`.

В двух терминалах:

```bash
npm run dev:backend
```

```bash
npm run dev:frontend
```

Backend поднимется на `http://localhost:4000`, фронтенд — на `http://localhost:5173`
(Vite проксирует `/api` на бэкенд, см. `frontend/vite.config.js`). Таблицы создаются
автоматически при первом запуске бэкенда.

### Демо-данные

```bash
cd backend
npm run seed
```

Полностью очищает таблицы users/orders/vacancies/reports и заполняет их реалистичными
данными: ~13 пользователей, ~40 заказов и ~15 вакансий по всем категориям и городам,
несколько жалоб. Пароль всех демо-заказчиков — `password123`. Админ создаётся тем же
скриптом: `admin@shabashka.kg` / `admin12345`.

Чтобы создать/повысить администратора вручную:

```bash
npm run create-admin -- email пароль "Имя"
```

## Импорт объявлений через Telegram-бота

Бот принимает скриншоты объявлений из WhatsApp и пересланные сообщения из чатов,
разбирает их через Groq в поля заказа и **публикует сразу** — на сайт, в
Telegram-канал, текстом в Threads и, последним, роликом в Instagram. Подтверждения
нет: скриншот на входе, опубликованное объявление на выходе.

Ничего не переспрашивается и когда данных не хватает: город без ответа становится
«Бишкек», незнакомая категория — «Другое», отсутствующий заголовок собирается
из первой фразы описания. Что именно дописали, бот пишет в ответе — подмена
не должна проходить молча.

Куда попадёт объявление, решает `listing_type` из разбора. Заказ и вакансия
становятся карточками на сайте. Всё остальное, что всё-таки является объявлением —
продажа дома или машины, аренда, «делаем ремонт под ключ», поиск работы для себя,
грузоперевозки, — уходит на **доску**: у такого на сайте карточки нет, а выбрасывать
его жалко, потому что публика у него та же. На плашке ролика такое объявление
подписано «ДОСКА №24» синим — не «объявление»: так сразу видно, куда идти на сайте,
и сколько объявление там проживёт.
Ролик, пост в Telegram-канале и ссылка
для WhatsApp делаются точно так же, разница только в адресе: у записки на доске
своей страницы нет, поэтому ссылка ведёт на `/board#p123`, а страница подсвечивает
нужное объявление. Живёт записка сутки — ролик её переживёт, и по ссылке из
старого поста доска честно скажет, что объявление пропало.

В подписи к ролику и в посте в Threads обязательны две вещи: **номер**, если он
есть в объявлении, и **ссылка** на карточку или доску. Без номера откликнуться из
ленты Instagram нечем — ссылки там не кликабельные, — а без ссылки не найти само
объявление. На кадр ролика телефон по-прежнему не выносится (см. ниже).

Одно и то же объявление автор рассылает сразу в несколько чатов, и скриншоты
приходят пачкой — повторы бот режет по телефону и сжатому заголовку
(`dedupHash` в `backend/src/telegram/imports.js`). Окно у этой проверки — **час**,
а не «навсегда», как было сначала. Смысл у неё остался ровно один: не дать одному
объявлению из пачки скриншотов встать на сайт тремя карточками, тремя постами в
канале и тремя роликами (последнее ещё и втрое жжёт часовой лимит Meta). Всё, что
старше часа, публикуется заново без вопросов: объявления живут долго, их постят
повторно, и мешать этому нечем. Записки на **доску** от проверки освобождены
совсем — там продают и сдают одно и то же изо дня в день.

Плата за автопубликацию — отсутствие модерации до неё: в чатах хватает сообщений,
которые объявлениями не являются, а чужой телефон попадает на сайт без ведома
владельца. Единственным фильтром остаётся сама модель, поэтому промпт требует
от неё осторожности: должно быть понятно, что именно предлагают или ищут. Отдельным
правилом отсеивается запрещённое — наркотики, «лёгкие деньги» без объяснения работы,
ставки, займы под проценты, обмен валют, продажа документов, — и оно же не даёт
такому проскочить на доску под видом объявления. Нечитаемый или обрезанный до
бессмыслицы текст тоже отбраковывается, чтобы модель не восстанавливала содержание
по догадке.

Что именно бот отбросил и почему — он пишет в ответе: строгий фильтр иногда
рубит настоящий заказ, а заметить это больше негде. Второй фильтр — кнопка
«🗑 Удалить с сайта» под каждым опубликованным объявлением. Она убирает
объявление с сайта, но не из Telegram-канала, Instagram и Threads — оттуда пост
придётся снять руками.

Команда `/stats` показывает, сколько объявлений опубликовано сегодня (день
считается по Бишкеку) и сколько роликов ещё собирается или загружается
на площадки. Те же две строки бот присылает сам после каждой пачки.

Команда `/now` (или просто «выпусти», «выпускай», «публикуй») выпускает ролик
из того, что уже стоит в очереди, не дожидаясь полной пачки — хоть из одного
объявления. Обычно ролик ждёт трёх объявлений одного типа, и это осмысленная
экономия: суточную квоту Instagram тратит пост, а не объявление. Но у ожидания
нет конца — тип, которого приходит по одному в день, не доедет никогда. Ролик
из одного объявления называется в единственном числе — «Вакансия дня», а не
«Вакансии дня». Если ролика ждут сразу несколько типов, бот спросит кнопками,
какой выпускать.

Переменные окружения (`backend/.env` локально, настройки сервиса на Render в проде):

| Переменная | Зачем |
|---|---|
| `GROQ_API_KEY` | ключ [Groq Console](https://console.groq.com/keys) — им разбирается скриншот. Можно вписать несколько через запятую — тогда скриншоты разбираются параллельно, по одному на ключ (см. ниже) |
| `TELEGRAM_BOT_TOKEN` | токен бота от [@BotFather](https://t.me/BotFather) |
| `TELEGRAM_ADMIN_IDS` | ID через запятую — кому разрешено публиковать |
| `TELEGRAM_WEBHOOK_URL` | адрес бэкенда, например `https://shabashka-backend.onrender.com` |
| `TELEGRAM_WEBHOOK_SECRET` | подпись вебхука, генерируется Render автоматически |
| `BOT_OWNER_EMAIL` | необязательно: от чьего имени публиковать (по умолчанию — первый админ) |
| `GROQ_MODEL` | необязательно: модель, по умолчанию `qwen/qwen3.6-27b` |
| `GROQ_REASONING` | необязательно: `low`/`medium` включает размышления модели — строже отбор, но втрое дороже по токенам. По умолчанию `none` |
| `FALLBACK_API_URL` | необязательно: запасной шлюз в формате OpenAI, куда уходит разбор, когда минутный лимит Groq выбран (см. «Запасной шлюз») |
| `FALLBACK_MODEL` | обязательно вместе с `FALLBACK_API_URL`: название модели на том шлюзе |
| `FALLBACK_API_KEY` | ключ к запасному шлюзу; локальному OmniRoute не нужен |
| `TELEGRAM_CHANNEL_ID` | необязательно: канал, куда бот сам постит опубликованное (бот должен быть его админом) |
| `INSTAGRAM_USER_ID` | необязательно: ID Instagram-аккаунта для автопостинга роликов |
| `INSTAGRAM_ACCESS_TOKEN` | необязательно: долгоживущий токен доступа к нему |
| `THREADS_USER_ID` | необязательно: ID профиля Threads — туда то же объявление уходит текстом, без ролика |
| `THREADS_ACCESS_TOKEN` | необязательно: токен Threads, отдельный от инстаграмного |
| `TELEGRAM_API_ID` / `TELEGRAM_API_HASH` | необязательно: автоимпорт из канала-источника (см. ниже), с [my.telegram.org](https://my.telegram.org) |
| `TELEGRAM_SESSION_STRING` | необязательно: строка юзер-сессии, один раз получить через `npm run telegram-login` |
| `SOURCE_CHANNEL` | необязательно: `@username` или id канала-источника, через запятую, если несколько |
| `SOURCE_LISTING_TYPE` | необязательно: список типов через запятую — `vacancy,order` (по умолчанию), можно добавить `board` или указать `all` |
| `SOURCE_REPORT_CHAT_ID` | необязательно: куда слать отчёт о публикации из канала (по умолчанию — первый из `TELEGRAM_ADMIN_IDS`) |
| `SOURCE_MAX_AGE_HOURS` | необязательно: не публиковать объявления старше стольких часов, по умолчанию `12` |
| `SOURCE_POLL_SECONDS` | необязательно: как часто опрашивать источники, по умолчанию `60` |

Объявление уходит на сайт, а если задан `TELEGRAM_CHANNEL_ID` — ещё и в канал.
Автопостинга в WhatsApp-каналы у Meta нет (публичного API для этого не существует),
поэтому бот вместо этого даёт ссылку `wa.me/?text=...` с готовым текстом — открывает
выбор чата в WhatsApp, а куда отправить (в свой канал или чат), решает админ.

### Ролики для Instagram

Вместе с публикацией бот собирает вертикальный ролик 720×1280 на 9 секунд: сцена
с объявлением в фирменных цветах сайта и концовка «Шабашка.com — найди работу».
Плашка выезжает из-за края, заголовок и описание проявляются строка за строкой,
цена выскакивает и досчитывается до своей суммы, логотип сайта появляется в подвале
кадра, а красный круг из центра открывает концовку. Всё, что не служит чтению, —
медленное: наезд на кадр и два еле заметных пятна на фоне.

Каждый кадр рисуется на канвасе (`backend/src/social/card.js`) и уходит сырыми
пикселями в stdin ffmpeg — промежуточных картинок на диске нет. Верстка считается
в координатах 1080×1920 и масштабируется при выводе, поэтому разметку кадра можно
править в привычных цифрах. И канвас, и ffmpeg приезжают npm-пакетами — ставить
что-то в систему на Render не нужно.

Фоновая музыка берётся случайным файлом из `backend/assets/music/` — там лежат
десять инструменталов Kevin MacLeod под CC BY 4.0, нарезанных по 20 секунд.
Лицензия требует называть автора, поэтому строка о треке автоматически уходит
в описание поста, а файл без записи в `credits.json` бот не берёт вовсе (см.
README в самой папке). Пустая папка — ролик уходит с тишиной. Подложить трек
из библиотеки Instagram нельзя: аудио оттуда выбирается только вручную
в приложении, а ролик, опубликованный по API, уходит со своей дорожкой.

Картинку для сетки профиля Instagram берёт не с первого кадра, а с 3.6-й секунды
(`COVER_AT` в `card.js`, уходит в API как `thumb_offset`): к этому моменту объявление
нарисовано целиком, тогда как в начале ролика кадр ещё пустой. В сетке видно не весь
кадр, а 4:5 из его середины — по 285 точек сверху и снизу срезается, — поэтому блок
с объявлением начинается ниже, чем выглядело бы правильным в полном кадре.

Телефон на кадр не выносится: в ленте Instagram он остался бы навсегда и без ведома
владельца, тогда как на сайте живёт вместе с объявлением, которое можно закрыть.

Если заданы `INSTAGRAM_USER_ID` и `INSTAGRAM_ACCESS_TOKEN`, бот публикует ролик как
Reels сам; Instagram скачивает mp4 с бэкенда по временной ссылке `/api/social/video/…`,
поэтому адрес из `TELEGRAM_WEBHOOK_URL` должен быть доступен извне. Без этих переменных
(или если публикация не удалась) бот просто присылает готовый mp4 с подписью в чат —
остаётся выложить вручную.

Соединение до серверов Meta рвётся часто (`fetch failed`), и почти всегда тот же
запрос проходит со второй попытки. Поэтому запросы, которые ничего не публикуют —
создание контейнера и опрос статуса, — повторяются сами (`backend/src/social/net.js`,
три попытки с растущей паузой). Публикацию слепо повторять нельзя: если запрос
дошёл, а ответ потерялся, второй такой же выложит второй ролик — поэтому на сетевом
сбое бот сначала спрашивает у контейнера его статус и считает дело сделанным, если
там уже `PUBLISHED`.

Threads публикуется сразу и без очереди — одновременно с сайтом и
Telegram-каналом, а не после них. Пост текстовый, ему не нужен ни собранный
mp4, ни обработка на стороне Meta. Instagram идёт через отдельную очередь с
90-секундной паузой между роликами (см. ниже): ему нужен готовый mp4, а сборка и
обработка на стороне Meta занимают минуты. Ролик собирается прямо перед
Instagram — единственной площадкой, которой он нужен. Часовой лимит Graph API у
Instagram и Threads общий на всё приложение, но текстовый пост — это два-три
вызова против трёх десятков на Reels, так что Threads эту очередь и не ждёт: от
такой уступки Instagram ничего не теряет. Площадки друг от друга не зависят в
обе стороны: не собрался ролик — Threads всё равно опубликован, а «User is
performing too many actions» в Instagram не стоит текстового поста.

Когда попытки всё-таки не хватило, бот не ждёт, что админ нажмёт кнопку: пробует
сам с растущей паузой — 5, 10, 20, 30, 45 минут и дальше раз в час, всего почти
шесть часов (`backend/src/telegram/bot.js`, `AUTO_RETRY_DELAYS`). Пауза растёт не
для красоты: сетевой сбой проходит за минуты, а «too many actions» — это троттлинг
на часы, и частые попытки упираются в него же, попусту тратя лимит приложения.

Повторяемый шаг здесь не только публикация, но и **сборка ролика**: если она
сорвалась (обычно `fetch failed` на музыке или шрифте), объявление уже стоит на
сайте, в Telegram и в Threads — терять Instagram незачем, и повтор просто соберёт
mp4 заново. В отчёте это строка Instagram, а не отдельная ошибка: сорвавшаяся
сборка касается только его.
Собранный ролик восемь часов лежит в памяти процесса, так что обычный повтор идёт
без пересборки и только по тем площадкам, где не вышло (уже опубликованное вторым
постом не полезет). К сообщению об ошибке приходит ещё и кнопка 🔁 «Попробовать
опубликовать ещё раз» — ей можно поторопить бота, не дожидаясь паузы. Если не
помогло за все шесть часов или процесс перезапустился, бот честно говорит, что
дальше только руками из сообщения выше.

### Текстовый пост в Threads

С `THREADS_USER_ID` и `THREADS_ACCESS_TOKEN` то же объявление уходит ещё и в
Threads (`backend/src/social/threads.js`) — но **текстом, без ролика**. API
отдельное от инстаграмного: свой хост `graph.threads.net`, свой ID профиля и свой
токен, даже если аккаунт заведён на том же Instagram. Площадки работают
независимо: протухший токен Instagram не мешает посту в Threads и наоборот, а в
чат приходит строка о каждой.

Без видео пост в Threads — это два-три вызова Graph API вместо трёх десятков.
Общий часовой лимит приложения от этого расходуется заметно медленнее — а он же
нужен инстаграмным Reels. Заодно ушла причина отказов вида «Threads не смог
обработать ролик (UNKNOWN)»: обрабатывать больше нечего.

Готовность контейнера всё равно спрашивается, хотя кодировать в текстовом посте
нечего: Meta просит дождаться её у любого контейнера и на попытку опубликовать
раньше отвечает «An unknown error occurred» — то есть ничем. Фиксированной паузы
нет, вместо неё опрос статуса: текст обычно готов сразу, так что в норме это один
лишний вызов. Не ответил и статус — публикуем всё равно: отказаться от поста из-за
неудачной проверки было бы хуже.

Отдельная история — **коды ошибок Meta**. Коды 1 (`API Unknown`) и 2
(`API Service`) она сама называет временными, и наружу они выходят той же строкой
«An unknown error occurred»; такие повторяются наравне с сетевым сбоем
(`isTransientApiError` в `net.js`). Остальные уходят наверх сразу — протухший
токен от повтора не оживёт, а попытка потратит вызов из часового лимита. В
сообщении об ошибке всегда есть шаг, код и `fbtrace_id`: по одной строке от Meta
не понять ни этапа, ни причины, а трейс — единственное, по чему её поддержка
найдёт конкретный запрос.

Текст поста собирается свой (`threadsText` в `video.js`), и причина не только в
лимите 500 знаков (эмодзи там считаются байтами UTF-8, поэтому и меряем так же).
Threads, в отличие от Instagram, делает ссылки кликабельными — значит, в пост идёт
прямой адрес объявления, а не приглашение в шапку профиля. Сначала собирается
обязательное — заголовок и ссылка, — а описание ужимается под остаток и режется по
словам. Указания автора трека здесь нет: музыка живёт в ролике, а ролика в этом
посте не будет.

Публиковать можно не больше 250 постов в сутки на профиль; при нынешнем потоке
объявлений до этого далеко.

### Автоимпорт из канала-источника (без пересылки руками)

Всё, что описано выше, публикуется само в момент, когда админ прислал боту
скриншот или переслал сообщение. Последнее ручное звено — сама пересылка. Если
вакансии постоянно берутся из одного чужого Telegram-канала (админ там просто
подписчик, не владелец), это звено тоже можно снять: `sourceWatcher.js` сам
следит за новыми постами канала и отдаёт их в тот же разбор и ту же публикацию,
что и обычные скриншоты — очередь, дедуп по телефону+заголовку, отчёт в чат,
повторные попытки соцсетей, всё общее.

**Почему юзер-сессия, а не бот.** Telegram Bot API отдаёт посты канала боту,
только если бот сам — администратор этого канала. Чужим каналом это не
устроить (владелец не пустит туда бота), поэтому здесь MTProto-клиент
([GramJS](https://gram.js.org/)) — по сути тот же Telegram, что открыт на
телефоне, только без интерфейса, под тем аккаунтом, который на канал уже
подписан.

**Настройка (один раз):**

1. Зайти на [my.telegram.org](https://my.telegram.org) → *API development
   tools* тем аккаунтом, который подписан на канал-источник. Получить
   `api_id` и `api_hash`, вписать в `backend/.env` как `TELEGRAM_API_ID` и
   `TELEGRAM_API_HASH`.
2. Из папки `backend` выполнить `npm run telegram-login` — скрипт спросит
   номер телефона, код из Telegram (и пароль двухфакторной аутентификации,
   если она включена) и выведет строку `TELEGRAM_SESSION_STRING=...`.
   Вписать её в `backend/.env` (и в переменные окружения сервиса на Render).
   Значение секретное: оно равносильно входу в аккаунт с нового устройства.
3. Задать `SOURCE_CHANNEL` — `@username` канала или его числовой id, через
   запятую, если источников несколько. Аккаунт, под которым получена сессия,
   должен быть подписан на каждый из них: иначе Telegram не отдаст историю, и в
   логе появится «не смог открыть "…"».
4. Перезапустить бэкенд — в логе должна появиться строка «Автоимпорт из
   канала включён: …».

**Фильтр по типу.** Группы смешанные (не только вакансии), а сайту нужны
работа и заказы, поэтому по умолчанию (`SOURCE_LISTING_TYPE=vacancy,order`)
публикуется только то, что модель уверенно распознала как вакансию или заказ —
остальное из этого источника молча пропускается, без публикации и без сообщения
в чат. Доска объявлений (`board` — продам-куплю-сдам) сюда не входит: чтобы её
тоже публиковать, добавьте `board` в список. `SOURCE_LISTING_TYPE=all` снимает
фильтр и публикует всё, что не отсеет сама модель (как из обычного скриншота).

**Что отсеивается до Groq.** Минутный лимит бесплатного Groq — примерно один
разбор картинки в минуту на ключ, а рекламный чат за вечер даёт сотню
сообщений. Поэтому до модели доходит не всё:

- второе и последующие фото одного поста (`grouped_id`) — текст объявления
  Telegram кладёт только в первое сообщение альбома, остальные дали бы лишние
  вызовы и дубли карточек на сайте;
- текст короче 15 символов («+», «салам») — объявлением он быть не может;
- текст без телефона — такое объявление всё равно не публикуется (откликнуться
  некуда), это видно по `handleParsed` в `bot.js`, так что разбор был бы
  выброшен впустую. Фото этой проверкой не отсеиваются: номер может быть
  нарисован на картинке;
- посты старше `SOURCE_MAX_AGE_HOURS` (по умолчанию 12 часов) — проверка стоит
  перед самым разбором, а не при приёме: пока пост стоял в очереди, он мог и
  устареть.

По длине очередь не обрезается специально: вакансия, написанная утром, вечером
всё ещё живая, и выбрасывать её только потому, что перед ней стоят другие, —
потеря на ровном месте, она бы дождалась. Порог по возрасту заодно страхует от
бесконечного роста очереди: если из групп приходит больше, чем Groq успевает
разбирать, отставание упирается в этот порог и дальше не растёт — протухшая
голова очереди отбрасывается мгновенно, без запроса к модели.

**Подпись под фото — это и есть объявление.** В рекламных чатах текст пишут
подписью к картинке. Если в подписи есть телефон и она достаточно длинная, пост
разбирается как текст: это примерно втрое дешевле по минутному лимиту и точнее,
чем читать тот же текст с фотографии. Иначе разбирается картинка, и подпись
уходит модели вместе с ней — помеченная как данные, а не как указания (текст из
чужого чата доверия не заслуживает).

**Очередь двухуровневая.** Скриншот, присланный админом руками, — это человек,
который ждёт ответа; поток из чужих групп подождёт. Поэтому посты из источников
встают в хвост очереди, а ручные скриншоты — перед первым фоновым. Без этого
один разговорчивый чат забивал бы очередь на полчаса вперёд.

**Куда приходит отчёт.** Публикация из канала идёт тем же путём, что и
скриншот, — значит, будет и то же сообщение в Telegram: карточка, кнопка «🗑
Удалить с сайта», статус по Threads/Instagram. По умолчанию оно уходит первому
из `TELEGRAM_ADMIN_IDS`; отдельный чат можно задать через
`SOURCE_REPORT_CHAT_ID`.

**Ограничение бесплатного Render.** Юзер-сессия держит постоянное соединение,
и на бесплатном тарифе оно обрывается, когда Render усыпляет сервис (см.
«Сон бесплатного Render» ниже) — самопинг покрывает почти сутки (5:00–1:00 по
Бишкеку), но не все 24 часа. Посты канала в это окно будут пропущены. Для
круглосуточной работы нужен платный тариф Render ($7) — там сервис не спит
вовсе.

У Groq бесплатный тариф без карты и без региональных ограничений (в отличие
от Gemini, который в Кыргызстане выдаёт нулевую квоту): 1000 запросов в сутки —
для одного бота с ручной модерацией этого хватает с запасом, платить не нужно.

Упирается всё не в суточный лимит, а в минутный: 8000 токенов в минуту при
~6800 на разбор одного скриншота, то есть подряд проходит ровно один.
Поэтому пачку скриншотов бот ставит в очередь (`backend/src/telegram/queue.js`)
и разбирает по одному, отвечая местом в очереди. Паузу между разборами он не
угадывает: Groq присылает остаток лимита в заголовках `x-ratelimit-*`, по ним и
считается ожидание — при свободном лимите его нет вовсе. Если лимит всё же
выбран, запрос повторяется через время, названное самим Groq в ответе 429.
Десяток скриншотов разбирается около десяти минут — если станет мало, лечится
платным Dev Tier у Groq, либо бесплатно: завести второй ключ на другом аккаунте
Groq и вписать оба в `GROQ_API_KEY` через запятую. У каждого ключа свой
независимый минутный лимит, и очередь (`backend/src/telegram/queue.js`) сама
разбирает по одному скриншоту на ключ параллельно — с двумя ключами пачка
идёт вдвое быстрее, менять код для этого не нужно.

### Запасной шлюз

Второй способ обойти минутный лимит — подключить другой сервис и отдавать ему
перелив. Подойдёт любой, кто говорит в формате OpenAI chat completions:

```
FALLBACK_API_URL=http://localhost:20128/v1
FALLBACK_MODEL=<название модели на том шлюзе>
FALLBACK_API_KEY=<ключ; локальному OmniRoute не нужен>
```

Адрес можно писать и без `/v1`, и сразу с `/v1/chat/completions` — недостающее
дописывается само.

Groq при этом остаётся основным: он проверен на кыргызском и русском тексте с
фотографий, а бесплатные модели на чужих шлюзах по этой части очень разные.
Запасной включается только тогда, когда ждать пришлось бы по-настоящему — ни у
одного ключа Groq не осталось минутного лимита (см. `pickLane` в
`backend/src/telegram/extract.js`). Если запасной шлюз не ответил (модель сняли,
квота кончилась, туннель отвалился), объявление не теряется: разбор возвращается
на Groq и просто ждёт его лимита, как раньше.

Модель на запасном шлюзе должна уметь картинки — иначе посты с фотографиями
разберутся мусором. Прежде чем оставлять её включённой, стоит прогнать через
бота несколько настоящих скриншотов и посмотреть, что она вернула.

**OmniRoute отдельно.** Он не облачный, а self-hosted: `npx omniroute` поднимает
шлюз на вашем компьютере (по умолчанию порт 20128). Бэкенд живёт на Render, и
`localhost` с вашей машины оттуда недоступен — значит, либо шлюз должен смотреть
наружу через туннель и компьютер быть включённым всегда, либо OmniRoute надо
поднимать отдельным сервисом рядом с бэкендом. Для круглосуточного бота проще
взять ключ у самого провайдера (у OmniRoute бесплатные модели — это чужие
бесплатные тарифы: Gemini, Cerebras, NVIDIA, Cloudflare) и вписать его адрес в
`FALLBACK_API_URL` напрямую, без шлюза посередине.

Эти 6800 складываются из промпта (~2300), картинки (~1900) и зарезервированного
ответа (2600) — Groq считает `max_completion_tokens` в лимит заранее, ещё до
самого ответа, поэтому запрос может не пройти целиком, сколько ни жди. Чтобы
вес не зависел от телефона отправителя, скриншот перед отправкой ужимается до
полутора мегапикселей: модель платит за плитки 28×28 точек, и снимок на 3–4
мегапикселя стоил бы вдвое дороже, ничего не добавляя к читаемости.

Свой Telegram ID бот подскажет сам — напишите ему что угодно, пока вас нет в
списке, и он ответит номером.

Без `TELEGRAM_WEBHOOK_URL` бот работает через long polling — это режим для
локальной разработки. В проде нужен именно вебхук: Render на бесплатном тарифе
засыпает без входящих запросов, и опрос Telegram обрывается, а входящий POST от
вебхука сервис будит.

## Деплой: бесплатный вариант без риска потерять базу

Три сервиса, каждый с бесплатным тарифом:

1. **Neon** или **Supabase** — Postgres. Создайте проект, скопируйте строку подключения
   (`DATABASE_URL`) — она не меняется даже при переходе на платный тариф в будущем.
2. **Render** — бэкенд (Node/Express). Подключите репозиторий, Render подхватит
   `render.yaml` (папка `backend`, `npm install` / `npm start`). В настройках сервиса
   на Render вручную впишите переменные окружения `DATABASE_URL` (из Neon/Supabase) и
   `PUBLIC_URL` (адрес фронтенда на Netlify, после его создания). `JWT_SECRET`
   сгенерируется автоматически. Домен у сайта кириллический, поэтому в `PUBLIC_URL`
   он записан в punycode-виде (`https://xn--80aaac0cyed.com`) — иначе его не поймут
   ни DNS, ни часть библиотек. В текстах объявлений бот разворачивает его обратно
   и показывает читаемое `шабашка.com/orders/131`.
3. **Netlify** — фронтенд (React/Vite). Подключите репозиторий, Netlify подхватит
   `netlify.toml` (сборка из папки `frontend`). В настройках сайта добавьте переменную
   окружения `VITE_API_URL`, указывающую на бэкенд на Render, например
   `https://shabashka-backend.onrender.com/api`.

Почему так: на бесплатном Render нет постоянного диска — при каждом перезапуске
файловая БД обнулялась бы. Neon/Supabase хранят данные отдельно и не зависят от
перезапусков бэкенда.

### Сон бесплатного Render

Render усыпляет бесплатный сервис после **15 минут** без входящих запросов, и
первый посетитель после простоя ждёт 30–50 секунд, пока контейнер поднимется.
Против этого работают три вещи:

1. **Самопинг** (`backend/src/keepalive.js`). Сервис раз в 12 минут дёргает свой
   же `/api/health` по адресу из `RENDER_EXTERNAL_URL` — таймер Render не
   успевает дойти до пятнадцати минут. Разбудить себя так нельзя: у спящего
   процесса таймеров нет, — это защита от засыпания, а не от сна.
   Круглые сутки не пингуем: в бесплатном плане 750 часов работы в месяц, а в
   месяце 744 часа, то есть запаса не остаётся вовсе. Поэтому окно — с 5:00 до
   1:00 по Бишкеку (`KEEPALIVE_FROM_HOUR` / `KEEPALIVE_TO_HOUR`): ~620 часов в
   месяц, и это те часы, когда на сайт реально заходят. Ночью сервис спит.
2. **Внешний пинг** — на случай, когда сервис всё-таки уснул (перезапуск, сбой
   сети): бесплатный монитор (cron-job.org, UptimeRobot) на
   `https://…onrender.com/api/health` с интервалом 10 минут. Только его расписание
   тоже стоит ограничить теми же часами, иначе 750 часов кончатся до конца месяца.
3. **Баннер «сервер просыпается»** (`frontend/src/components/WakingBanner.jsx`).
   Первый заход всё равно когда-нибудь окажется холодным, и пустой скелет на
   полминуты читается как «сайт сломан». `api.js` считает незакрытые запросы,
   и если ответа нет 5 секунд — сверху появляется объяснение.

Когда трафик вырастет, честное решение — платный тариф Render ($7): он не спит
вовсе, и вместе со сном уходит ограничение в 750 часов. Кроме скорости первого
захода это лечит и `robots.txt` с `sitemap.xml`: Netlify проксирует их на Render
и ждёт ответа около 26 секунд — на холодном старте поисковик получает ошибку.

| GET | `/api/orders/:id` | публичный | заказ по id (увеличивает счётчик просмотров) |
| GET | `/api/orders/categories` | публичный | список категорий |
| GET | `/api/orders/category-counts` | публичный | количество открытых заказов по категориям |
| POST | `/api/orders` | по токену | создать заказ |
| GET | `/api/orders/mine` | по токену | мои заказы |

| DELETE | `/api/orders/:id` | по токену, владелец | удалить заказ |

## Планы на мобильное приложение

Бэкенд — чистый REST API с JWT (без сессий/cookie), поэтому его можно напрямую
подключить к будущему приложению на React Native: авторизация, список заказов,
публикация заказа и переход в WhatsApp работают без каких-либо изменений на сервере.
